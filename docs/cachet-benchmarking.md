# Cachet — Benchmarking Methodology

> **Status:** v1, 2026-09-05.
> **Companion to:** [`cachet-build-plan.md`](./cachet-build-plan.md)
>
> Every number in the README comes from here. If a claim can't be produced by `make bench-report`,
> it doesn't go in the README.

---

## 1. Why this document exists

Cachet's entire pitch is *"other caches ask you to trust them; this one proves it."* A project
making that claim cannot have sloppy benchmarks. The measurement discipline **is** the product
thesis, applied to itself.

Practically: benchmarking is built in **Phase 0, before any caching code exists.** Not because it's
satisfying, but because a baseline you collect after building the thing you want to look good is
not a baseline — it's a rationalization.

### The four rules

1. **Baseline first.** The uncached number is collected before the first line of cache code.
2. **One workload, one environment, one table.** Every phase adds a row. Same generator, same
   hardware, same seed. A row you can't compare to the row above it is decoration.
3. **Results are machine-readable.** JSON in `bench/results/`, README table generated by script.
   Hand-typed numbers drift, and drift reads as dishonesty even when it's laziness.
4. **Publish what loses.** A phase that fails to improve its metric stays in the table with the bad
   number and a sentence explaining it. This is the single cheapest credibility purchase available.

## 2. What we are actually measuring

Cachet makes five claims. Each maps to exactly one primary metric.

| Claim | Primary metric | Workload |
|---|---|---|
| Caching reduces read cost | **Origin QPS** and read p99 | W2 |
| Invalidation is exact | **Staleness violations / total reads** | W2 + writes |
| Leases bound origin load | **Peak origin QPS for one key under stampede** | W3 |
| Admission is self-tuning | **Redis bytes per unit hit rate**, write p99 | W4 |
| Correctness is verifiable | **Faults caught and explained / faults injected** | Chaos suite |

Anything not on this list is diagnostic, not a headline. Resist reporting throughput as the
headline — you are not going to out-throughput a funded team on a laptop, and it isn't the claim.

## 3. The traps — get these right or the numbers are fiction

This section is the reason to read this document. Each of these is a way benchmarks routinely lie,
and most portfolio projects fall into at least three.

### 3.1 Coordinated omission — the big one

**The trap:** a *closed-loop* generator sends a request, waits for the response, then sends the
next. If the system stalls for 2 seconds, the generator simply doesn't send requests during the
stall. The stall never appears in the latency distribution. Your p99 looks great precisely because
the system was too slow to be measured.

This is catastrophic for Cachet specifically, because **stampedes and invalidation storms are
exactly the stall-shaped events we claim to fix.** A closed-loop harness would hide the problem and
then hide the fix.

**The fix — open-loop generation with intended-start-time tracking:**

```go
// Requests are scheduled at a fixed rate, independent of whether
// previous ones have completed. Latency is measured from the time the
// request WAS SUPPOSED to start, not from when a worker got to it.
intendedStart := runStart.Add(time.Duration(i) * interval)
if d := time.Until(intendedStart); d > 0 {
    time.Sleep(d)
}
// ... issue request ...
hist.RecordValue(time.Since(intendedStart).Microseconds())  // NOT time.Since(actualStart)
```

Plus HdrHistogram's correction as a second layer:
`hist.RecordValueWithExpectedInterval(v, expectedInterval)`.

**Rule: the harness is open-loop from day one.** Retrofitting this later invalidates every number
collected before it.

### 3.2 Averaging percentiles

**The trap:** you have three runs with p99s of 10 ms, 12 ms, 11 ms, so you report 11 ms. That number
is meaningless — percentiles don't average. Same for merging across shards or workers.

**The fix:** merge the *histograms*, then compute the percentile once from the merged distribution.
HdrHistogram supports this directly. Every worker records into its own histogram; the harness merges
them at the end.

### 3.3 Measuring the warmup

**The trap:** cold caches, empty connection pools, unJIT'd code paths, and MyRocks' block cache
still filling. The first 30 seconds of any run are not the steady state.

**The fix:** explicit phases — `warmup` (discarded), `measure` (recorded), `drain`. Record which is
which in the results JSON. **Warmup duration is a declared parameter, not a vibe.**

Cachet-specific: a warmup long enough to fill the cache *inflates* hit rate; too short *deflates*
it. Declare the warmup policy per workload and keep it constant across phases, or the rows stop
being comparable.

### 3.4 A single run

**The trap:** one run, one number. Run-to-run variance on a developer machine is routinely 20–30%,
which is larger than most of the effects being measured.

**The fix:** **minimum 3 runs**, report median and the min–max spread. If the spread exceeds the
effect you're claiming, you have not measured anything — say so and fix the environment before
reporting.

### 3.5 Uniform key distributions

**The trap:** uniform random keys across 10M rows means almost no key is ever hot, so the cache hit
rate is near zero and every caching effect vanishes. It also makes stampedes impossible.

**The fix:** **Zipfian, θ = 0.99** (the YCSB default) as the standard. Keep a uniform workload (W1)
as a sanity check only — it is the control, never the headline.

Run a **skew sweep** (θ = 0.7 / 0.9 / 0.99 / 1.2) once, in Phase 4. Showing where adaptive admission
stops helping is more interesting than the single best number.

### 3.6 Measuring the wrong side

**The trap:** claiming "leases fix stampedes" and then showing client latency. Client latency may
barely move; the database load is what collapses.

**The fix:** instrument the **origin** directly. Origin QPS, MySQL connection count, MySQL CPU. For
the stampede claim, the headline graph is *origin QPS over time*, with the invalidation marked.

### 3.7 Benchmarking Docker Desktop and calling it hardware

**The trap:** Docker Desktop on macOS runs a VM with a virtualized filesystem. I/O latency there is
unpredictable and unrepresentative, and MyRocks is I/O-sensitive.

**The fix:** develop locally, but collect **headline numbers on a dedicated Linux host** — a cheap
bare-metal or a consistent cloud VM. Record the environment in every results file (§6) and state it
in the README. "Measured on a MacBook under Docker Desktop" is an acceptable disclosure; silently
implying otherwise is not.

## 4. Environment and reproducibility

Every run records its environment. Non-negotiable fields:

```json
{
  "env": {
    "host": "dedicated-linux | docker-desktop-macos",
    "cpu": "AMD EPYC 7402P, 24c/48t", "cores_available": 24,
    "ram_gb": 64, "disk": "NVMe SSD",
    "os": "Ubuntu 24.04", "kernel": "6.8.0",
    "go_version": "go1.25.x",
    "images": {
      "mysql": "percona/percona-server@sha256:...",
      "redis":  "redis@sha256:..."
    },
    "cachet_commit": "a1b2c3d",
    "noise_controls": ["cpu governor=performance", "no other workloads", "THP=never"]
  }
}
```

**Pin image digests, not tags.** `percona-server:8.0` silently changing underneath you between
Phase 2 and Phase 5 will produce a "regression" you'll spend a day chasing.

## 5. Workload catalogue

Defined in `bench/workloads/*.yaml`. Dataset: **10M rows, ~1 KB values** unless stated.

| ID | Name | Mix | Distribution | Purpose |
|---|---|---|---|---|
| **W1** | Uniform control | 95R / 5W | Uniform | Sanity check; the control, never a headline |
| **W2** | Realistic read-heavy | 95R / 5W | Zipf θ=0.99 | **The primary workload.** Every phase row uses this |
| **W3** | Stampede | 100R burst on 1 key | Single hot key | Lease claim. Invalidate, then 10k concurrent readers |
| **W4** | Mixed admission | 90% keys 100:1 R:W, 10% keys 1:5 R:W | Zipf θ=0.99 | Adaptive admission claim |
| **W5** | Write-heavy | 30R / 70W | Zipf θ=0.99 | Proves Cachet **declines to cache** rather than degrading |
| **W6** | Skew sweep | 95R / 5W | θ ∈ {0.7, 0.9, 0.99, 1.2} | Where the effects begin and end |

W5 matters more than it looks. A cache that gets slower on write-heavy workloads and doesn't notice
is a liability; showing that admission *correctly refuses* is a genuine correctness result.

### Run parameters (constant across phases)

```yaml
warmup:      60s      # discarded
measure:     300s     # recorded
runs:        3        # median reported, min-max shown
rate:        <fixed>  # open-loop; set per workload, held constant
seed:        42       # same key sequence every run
```

## 6. Metrics catalogue

| Group | Metric | Source | Notes |
|---|---|---|---|
| **Client** | read p50/p90/p99/p99.9, write p99, throughput, errors | HdrHistogram in harness | Merged histograms only |
| **Cache** | hit rate, negative hit rate, memory bytes, evictions, lease grants, lease waits | Redis INFO + engine counters | |
| **Origin** | **QPS**, connection count, CPU%, MyRocks read amp | MySQL + exporter | The real cost metric |
| **Consistency** | violations/sec, **nines per level**, invalidation lag p99 | Sextant | Phase 4c onward |
| **Efficiency** | reads served per Redis MB, reads served per origin core | Derived | The honest "value" metrics |

### Derived headline metrics

- **Cache value** = `(uncached p99 − cached p99) / uncached p99`
- **Origin reduction** = `1 − (cached origin QPS / uncached origin QPS)`
- **Memory efficiency** = `hit rate / Redis GB` — the metric adaptive admission must improve

## 7. Measuring consistency — the hard part

Latency is easy. Correctness needs a real method, and this is where the project earns its claim.

### The probe protocol

A dedicated writer maintains a set of **probe keys** separate from the load workload:

1. Writer writes `(key, seq, hlc_version, wall_time)` where `seq` increases monotonically per key.
2. Readers read probe keys through Cachet at each consistency level, logging
   `(key, seq_seen, version_seen, read_start, read_end, level, session_token)`.
3. All events go to an append-only log.

### Offline checking

After the run, `bench/checker` replays the log and checks the invariants:

| Level | Invariant | Violation |
|---|---|---|
| `STRONG` | Read reflects the latest committed write before `read_start` | Any older value |
| `SESSION` | Read version ≥ the session's write watermark | `version_seen < watermark` |
| `SESSION` | **Monotonic reads** — within a session, `seq_seen` never decreases | Any decrease |
| `BOUNDED(t)` | `read_start − commit_time(seq_seen) ≤ t` | Exceeds `t` |
| `EVENTUAL` | Converges within the propagation bound | Never converges |

**Report as nines:** `1 − (violations / total_reads)`, e.g. `99.997%`.

Note the honest caveat to state in the README: with a few million probe reads you can credibly
demonstrate four to five nines. Claiming ten nines requires a volume of observations you will not
generate on this hardware. **State the number of observations alongside the nines.** A nines figure
without a sample size is meaningless, and saying so is itself a signal.

### Relationship to Jepsen

Jepsen/Elle is the gold standard for this kind of checking. The probe checker above is a deliberate,
narrower instrument: it verifies the specific guarantees `CONSISTENCY.md` claims, rather than
general linearizability. Say that explicitly rather than implying Jepsen-grade verification.

**Stretch goal (Phase 5+):** an Elle-compatible history export. Worth mentioning in the writeup as
future work whether or not you build it.

## 8. Results format and automation

One JSON file per run: `bench/results/<phase>_<workload>_<timestamp>.json`.

```json
{
  "schema_version": 1,
  "phase": "4a-leases",
  "workload": "W2",
  "env": { "...": "see §4" },
  "params": { "warmup_s": 60, "measure_s": 300, "rate": 50000, "seed": 42, "zipf_theta": 0.99 },
  "runs": 3,
  "client": {
    "read_p50_us": 210, "read_p99_us": 1840, "read_p999_us": 9200,
    "write_p99_us": 3100, "throughput_rps": 49987, "errors": 0,
    "spread": { "read_p99_us": [1790, 1910] }
  },
  "cache":  { "hit_rate": 0.991, "negative_hit_rate": 0.04, "memory_bytes": 4294967296,
              "lease_grants": 12043, "lease_waits": 981220 },
  "origin": { "qps": 4512, "peak_qps": 8800, "cpu_pct": 22.4 },
  "consistency": { "observations": 4200000, "violations": 12, "nines": 0.9999971 }
}
```

`make bench-report` reads every file, picks the latest per (phase, workload), and **regenerates the
README table**. Nobody types a number into the README, ever.

### CI regression gate

On every PR, run W2 at reduced duration (60 s measure, 1 run) and fail if:
- read p99 regresses > 10% vs the baseline on `main`
- hit rate drops > 2 points
- **any consistency violation appears at `SESSION` or `STRONG`** — this one is a hard zero

The consistency gate is the one that matters. A performance regression is a bug; a consistency
regression is the product being false.

## 9. Per-phase benchmark obligations

Each phase must produce these before it is considered done.

| Phase | Must produce |
|---|---|
| **0** | W1 + W2 uncached, 3 runs, JSON committed, README row generated. **Origin QPS and p99 recorded.** |
| **1** | W2 with TTL cache. Hit rate, p99, origin reduction. **Staleness measured and knowingly bad** — this motivates Phase 2 |
| **2** | W2 with CDC invalidation. **Staleness: minutes → sub-second**, with the number |
| **3** | W2 with sync invalidation. **Read-own-writes suite green.** Write p99 recorded — Phase 4c needs this as its comparison point |
| **4a** | **W3 stampede: origin QPS over time, with and without leases.** This is the money graph |
| **4b** | W4 + W5. Equal hit rate at lower memory and lower write p99 vs static. **Skew sweep W6.** Publish it if it loses |
| **4c** | Live nines per level, with observation counts. Dashboard screenshot |
| **5** | 9 faults; per fault: detected y/n, time to detect, trace excerpt, recovery behaviour |
| **6** | InnoDB vs MyRocks under identical W2 — the cache-value delta between engines |

## 11. Anti-goals

Things deliberately not measured, so the scope stays honest:

- **Absolute peak throughput.** Not the claim; not winnable on this hardware.
- **Comparisons against ReadySet/PolyScale on their own turf.** Complex analytical SELECTs are
  explicitly out of scope. Benchmarking a competitor at something you didn't build for is the
  oldest bad-faith move in the genre, and readers spot it.
- **Multi-region latency.** Deferred with cross-region replication.
- **Cost in dollars.** Cloud pricing is a moving target and invites a fight about instance types
  instead of about the system.
